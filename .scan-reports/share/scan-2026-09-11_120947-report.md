# Security scan: EdgeMesh

Scanned: ~/code/EdgeMesh on 2026-09-11
Raw log: .scan-reports/scan-2026-09-11_120947.log
Branch: codex/codebase-review-fixes (working tree, includes uncommitted files)

## Verdict: REVIEW BEFORE USING

The first-party code is clean. The pinned Windows/Python 3.12 dependency set
(`pyproject.toml`, `constraints/windows-py312.txt`, `requirements-cpu-test.txt`,
and the installed `.venv`) carries 13 packages with known CVEs, and Pillow and
Transformers among them are reachable from user-supplied files. The Linux
Python 3.14 environment (`.venv_linux`) has zero known vulnerabilities.

## How the scan ran

The in-place run stalled: Trivy's secret scanner walked 11 GB of virtual
environments (`.venv` 3.2 GB, `.venv_linux` 7.7 GB) over the WSL DrvFS mount.
The scanner script has no option to skip those directories. The scan therefore
ran on a scratch copy of the tree with these exclusions: `.venv`, `.venv_linux`,
`Depth Models`, `checkpoints`, `onnx_models`, `Morgue`, `build`, `dist`, `logs`,
caches, and `.git`. Both venvs contributed only their `*.dist-info/METADATA`
files so installed versions were still audited. Paths in the log are rewritten
to the real repo path.

Two scanner-script defects affected the run; both are documented under Caveats.

## What actually matters

Ordered by severity, reachability, and fix availability.

1. **Pillow 11.3.0 (18 advisories, fix 12.3.0).** Native heap corruption and
   out-of-bounds writes in PSD, PCF/BDF font, GD, JPEG2000, PDF and TGA
   parsing, plus decompression bombs. Reachable: `MeshTools/mesh_tools.py`
   opens user-selected texture images with `Image.open`, `depth_to_3d.py`
   imports PIL, and the Transformers image processors decode input images
   with Pillow. A crafted image opened in EdgeMesh can crash the process or
   worse. Fix is a drop-in pin bump; already proven in `.venv_linux`.

2. **Transformers 4.56.2 (11 advisories; 5 have no fix, fixes for the rest
   start at 5.0.0).** All are code execution during model or checkpoint
   loading (X-CLIP, SEW, SEW-D, HuBERT, GLM4 conversion paths; `Trainer` RNG
   state; LightGlue; path traversal on download before 5.10.0). Reachability
   is limited: `model_store.py` loads only depth-estimation and SAM2 models,
   pins each to a recorded revision, sets `trust_remote_code=False`, and
   defaults to `local_files_only` until the user enables downloads. The
   path-traversal advisory (CVE-2026-9856) does apply when downloads are
   enabled against an attacker-controlled repo. The fix is a major upgrade to
   5.x, which changes the dependency closure (huggingface-hub 1.x with httpx,
   typer, rich, hf-xet). `.venv_linux` already runs 5.14.1, so the code is
   known to work with 5.x.

3. **Torch 2.8.0 (8 advisories, fixes 2.9.0 to 2.13.0; one with no fix).**
   Memory corruption in `torch.jit.script`, `lstm_cell`, `unpack_sequence`,
   `linalg.lu`, and a `weights_only` unpickler bypass (CVE-2026-24747, fix
   2.10.0). The unpickler one matters most: it undermines the safe default
   that protects the `torch.load` calls below. The no-fix advisory
   (CVE-2026-4538) concerns the pt2 archive loader, which EdgeMesh does not
   use. Fix: torch 2.13.0 with torchvision 0.28.0, both available as cp312
   Windows wheels and already running in `.venv_linux`.

4. **Transitive web and utility packages (9 packages).** urllib3 2.5.0
   (redirect header leak, decompression bombs), requests 2.32.5 (predictable
   temp path), werkzeug 3.1.3 and flask 3.1.2 (Windows device-name path
   join, cache header), click 8.3.0 (`click.edit` injection), filelock 3.19.1
   (symlink TOCTOU), fonttools 4.60.1 (varLib file write), idna 3.10
   (denial of service), pygments 2.19.2 (lexer DoS), setuptools 80.9.0
   (MANIFEST file inclusion). Flask, werkzeug, and click enter only through
   Open3D's Dash web dependency and are never served by EdgeMesh. urllib3 and
   requests are used by huggingface-hub for model downloads. All have
   drop-in fixes.

5. **Semgrep `torch.load` without `weights_only` (2 findings).**
   `torch_utils.py:48` and `torch_test.py:12` call `torch.load(path)` with
   the default. On torch 2.6 and later the default is `weights_only=True`, so
   this is mitigated, but `torch_test.py` is a scratch script that exits
   midway and is excluded from packaging. `depth_anything.py:41` has the same
   pattern; `model_store.py:463` already passes `weights_only=True`.
   Recommendation: pass `weights_only=True` explicitly in the two live
   files and delete `torch_test.py`.

**False positives, explained:**

- GuardDog `api-obfuscation` at `embedded_viewport.py:793` and
  `feature_workflows.py:235`: both are `getattr(obj, method)(...)` where
  `method` is a string literal from a fixed table (`set_view`,
  `reset_camera`, `setValue`, `setCurrentText`). Ordinary Qt dynamic
  dispatch, no network or eval.
- Semgrep `detected-jwt-token` in `itsdangerous-2.2.0.dist-info/METADATA`:
  the example token from the itsdangerous README, inside package metadata.
- OSV rows sourced from `requirements.txt` and `MeshTools/requirements.txt`
  (torch 1.8.1, pillow 9.5.0, scipy 1.9.3, idna 3.9.0, nbconvert 7.9.2,
  transformers 5.9.0): those files are unpinned. osv-scanner 2.3.8 guesses a
  version for unpinned lines and even adds packages that are not listed
  (nbconvert). Nothing installed matches those versions. Ignore them; the
  pinned closure is the truth.

**Trivy** found no leaked secrets and no misconfigurations across the source
tree, Notes, docs, and workflows. It reported no vulnerabilities because the
only manifests it parses by name are unpinned; pip-audit and OSV covered the
pinned closure instead.

## Recommended fixes

All target versions below were published between 2026-02 and 2026-07, so
every one is older than the 7-day minimum-package-age rule. They are the
versions already installed and working in `.venv_linux`.

Drop-in pin bumps for the Windows 3.12 profile. Apply to `pyproject.toml`,
`constraints/windows-py312.txt`, and the setuptools line in
`.github/workflows/tests.yml`:

```
pillow      11.3.0 -> 12.3.0
torch       2.8.0  -> 2.13.0
torchvision 0.23.0 -> 0.28.0   (must match torch)
setuptools  80.9.0 -> 83.0.0   (also the build-system requires)
urllib3     2.5.0  -> 2.7.0
requests    2.32.5 -> 2.34.2
werkzeug    3.1.3  -> 3.1.8
flask       3.1.2  -> 3.1.3
click       8.3.0  -> 8.4.2
filelock    3.19.1 -> 3.32.2
fonttools   4.60.1 -> 4.63.0
idna        3.10   -> 3.18
pygments    2.19.2 -> 2.20.0
```

These bumps keep the closure self-consistent: torch 2.13.0 needs
`setuptools>=77`, `sympy>=1.13.3`, `networkx>=2.5.1`, `typing-extensions>=4.10`,
all already satisfied; torchvision 0.28.0 pins `torch==2.13.0`; requests
2.34.2 and flask 3.1.3 are satisfied by the existing charset-normalizer,
certifi, blinker, jinja2, markupsafe pins.

Transformers cannot be bumped by editing pins. 5.14.1 requires
`huggingface-hub>=1.5,<2` (which replaces requests with httpx, httpcore,
h11, anyio, hf-xet), `typer` (rich, shellingham, markdown-it-py, mdurl),
`regex>=2025.10.22`, and `safetensors>=0.8.0`. Regenerate the Windows closure
per `docs/Dependency_Validation.md`: fresh 3.12 venv, install
`.[depth,spacemouse]` with transformers 5.14.1, traverse installed metadata,
rewrite `constraints/windows-py312.txt`, then run `pip check` and the
workflow's unittest steps.

After either change, validate on Windows:

```
python -m pip install --no-deps -r requirements-cpu-test.txt
python -m pip check
python -m unittest discover -s tests
```

Code fixes (not vulnerabilities, not in the script):

- `torch_utils.py:48` and `depth_anything.py:41`: add `weights_only=True`.
- Delete `torch_test.py` (scratch script, already excluded from packaging).

Fix script: .scan-reports/scan-2026-09-11_120947-fix.sh

## Caveats

- A clean scan is not proof of safety. GuardDog and Semgrep are heuristics.
- What was scanned: the git working tree on branch `codex/codebase-review-fixes`
  with uncommitted changes, not a published wheel or the `main` branch. The
  `MeshTools/` nested repo was included. Model weight files were excluded.
- Two defects in the bundled `scan-download` script affected this run and
  will affect every scan from a working directory that contains
  `requirements*.txt` files:
  1. Line 107 uses an unquoted `-name requirements*.txt` in `find`. The shell
     expands the glob against the current directory, `find` errors out,
     ecosystem detection returns "none", and GuardDog and pip-audit are
     silently skipped. Quote the pattern. GuardDog was re-run by hand here.
  2. Trivy has no skip for `.venv*`, `venv`, or model directories, so
     secret scanning crawls every installed package. Add those to
     `--skip-dirs`, or honor an env var such as `SCAN_SKIP_DIRS`.
- pip-audit ran with `--no-deps --disable-pip` on pinned lists only. The
  script's own `pip-audit -r requirements.txt` would have pip-installed the
  whole unpinned dependency set, including CUDA torch, and was not run.
- Honor the 7-day minimum-package-age rule on any version other than the
  ones listed above.

## Reproduce this scan

The scan ran with the **scan-source** plugin from the Chameleon Labs
marketplace (GuardDog malware heuristics, Trivy + OSV-Scanner CVE/secret
scanning, Semgrep SAST).

Install the plugin in Claude Code:

```
/plugin marketplace add Chameleon-Labs-LLC/plugins
/plugin install scan-source@chameleon-labs
```

Or from the terminal:

```bash
claude plugin marketplace add Chameleon-Labs-LLC/plugins
claude plugin install scan-source@chameleon-labs
```

Verify with `/plugin list`, then run `/scan-source ~/code/EdgeMesh`. On
first use the skill installs the scanner CLIs it needs (pipx + static binaries
in `~/.local/bin`, no sudo). Reports land in `<target>/.scan-reports/`.
